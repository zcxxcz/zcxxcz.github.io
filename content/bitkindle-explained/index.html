怎么造出 C 编译器？

先从首页的 Mario 动图移开视线。这个项目最有意思的，是一路追问下去：编译器能造程序，那第一把编译器，又是谁造的？

先记住这一句：BitKindle 从一份很小的可执行工具出发，借助已有源码，逐层造出更强的工具，最终得到能编译自己的 C 工具链，再用它编译出 Mario 等应用。[1]

01 / 先认清三样东西

代码是图纸，工具把它造出来。

把“描述程序的文字”和“已经能运行的程序”分开。很多困惑，到这里就解开了一半。

A /

源码：给人读的图纸

用 C、汇编等语言写出的说明。放在那里，还不能直接让 CPU 执行。

compiler.c 描述编译器；
mario.c 描述游戏规则。

B /

编译工具：造程序的工具

编译器翻译代码；装配器处理汇编表示；链接器拼合目标文件、处理引用。

它们自己也是程序，
需要先有一份能运行的版本。

C /

EXE：造好的成品

Windows 能装载的可执行文件。包含机器指令，以及操作系统需要的文件结构。

成品可以是游戏，
也可以是下一把编译器。

平常写程序安装现成编译器 → 翻译你的源码 → 得到程序
BitKindle 额外展示的事先用小工具造编译器 → 再用它翻译程序
02 / 把链条拆开

每一步，只跨过够得着的那一级。

下面把实际的多级构建合并成七步。点击阶段或播放导览，看看“已有的工具”，怎样把“下一层源码”变成新工具。

关键是“接力翻译”。
每一层都需要：已经能运行的旧工具，以及事先写好的新工具源码。构建这套工具链无需先安装 MSVC、GCC、Clang、Windows SDK 或外部链接器，也不下载依赖；第一把工具来自种子。[5]

03 / 最容易卡住的一步

“用 C 写的 C 编译器”，怎么启动？

一种语言能描述编译器，与电脑上已有可执行的编译器，是两件事。前面的链条，就是为了先造出那份能运行的版本。

想象一份“造印刷机的说明书”。它能被印刷，并不要求它印刷自己。先用旧机器印出第一份，之后才可以用新机器继续印。

  1. 由前一层工具造出第零代。
    C1 源码是文字，第零代 C1 则是已经能执行的程序。
  2. 把编译器源码，当作普通输入。
    第零代编译 host/compiler.c 和完整运行库，链接成第一代。
  3. 第一代重复同一份工作。
    同样源码生成第二代，再比较产物。这里是在实现已有设计，不是创造新设计。

“两代相同”能说明什么？说明这一轮自编译的输出稳定。一个稳定存在的错误，也可能每次生成相同结果。所以还需要功能测试；一致性本身不能保证所有 C 程序都编译正确。[1]

05 / 它到底厉害在哪里

把“编译器从哪里来”摊开给你看。

我的解读：它的价值主要在可追踪的构建路径，以及逐层搭工具的工程方法。看项目时，值得沿这条路径往前追。

可以从中学到的东西

  • 小起点：起始可执行种子很小，可以把它当成理解整条链的入口。
  • 阶梯式设计：第一层不必全能，只需足以造出下一层。
  • 自托管的具体过程：编译器也像普通应用一样，被已有编译器编译。
  • 工具链的分工：编译、链接、运行库与操作系统，各自承担工作。

理解时要带着的边界

  • 系统底座仍在：需要 Windows x64 与 PowerShell 5.1。
  • 种子之外还有源码：后续工具、库和应用的设计，并不装在那 3.5 KiB 里面。
  • 语言支持有范围：有 C89 和不少 C99 功能，作者未宣称完整 C99 符合性。
  • 生态兼容性有限：自制 .c1o 不等于通用 COFF；通用 SDK 头文件等兼容性不在当前范围。

范围按引用版本核对。[5 总览] [6 限制]

为什么它不等于“3.5 KiB 的 C 编译器”？

3.5 KiB 指第一份 A0 装配器机器码的大小。C0、各层 C1、链接器和运行库源码都是额外输入；最终 C 编译器是这条长链的产物。

PowerShell 是不是偷偷完成了编译？

项目的分工是：PowerShell 解码起始字节，运行工具、处理文件、准备文本并检查结果；后续机器码由自制工具生成。可以把它理解为生产线调度员。PowerShell 和 Windows 都是这条链的已有底座。[1]

我想复现，应该从哪里开始？

需要 Windows x64、Windows PowerShell 5.1 和完整源码。根目录 build-all.ps1 是入口：默认构建工具链并保留一致性检查，但不跑回归；-All 加编译示例；-Full 做更完整验收。Mario 的构建与测试另有入口。Mac 上可阅读本页，构建则按项目的 Windows 要求操作。具体命令与成功判据见原版快速开始。
